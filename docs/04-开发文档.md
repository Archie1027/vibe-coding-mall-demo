# 智采商城｜开发与交付指南

版本：v0.2 · 日期：2026-10-20 · 状态：实施设计稿，尚未创建项目仓库或执行应用测试

## 1. 架构决策

### ADR-01 模块化单体

一个Spring Boot后端进程、一个MySQL逻辑数据库，按Maven模块划分业务边界。顾客商城与管理端各为独立Vue应用。同步核心业务共享本地事务；通知、索引、导出通过事务outbox异步处理。模块拆分不等于微服务，不引入跨服务分布式事务。

### ADR-02 学习方式

主项目使用Spring Boot+Spring MVC+MyBatis。开始时单独做商品分页查询的传统SSM对照练习，学习容器、DispatcherServlet、DataSource、SqlSessionFactory、事务管理器，再迁入Boot主线；该练习不作为生产模块。

先使用MyBatis接口+XML编写关键SQL，理解映射与事务，不用代码生成器掩盖库存、订单、财务操作。普通CRUD可在理解后生成。

### ADR-03 身份与前端

Spring Security负责身份与权限；使用安全随机数生成不透明Bearer令牌，服务端存哈希及主体引用，Redis中设置2小时TTL。浏览器仅存内存；不使用自动附带的认证Cookie。刷新后重新登录为已记录的首版取舍，不引入未定义的refresh-token协议。

用户自助注册只产生顾客；员工由管理员创建。每次请求从权限缓存或数据库核实有效权限，角色/停用变更主动失效缓存。Redis失效时认证失败关闭，不能降级为匿名有权限。登录失败限流独立于业务限流。

## 3. 仓库与模块结构

建议仓库名`zhicai-platform`。以下是拟创建文件路径，不代表这些代码已生成。

| 路径 | 职责 |
|---|---|
| `pom.xml` | 父POM、dependencyManagement、插件版本 |
| `platform-common/` | ID、分页、异常、最小共享接口，不放所有业务实体 |
| `platform-identity/` | 顾客/员工、权限、会话、审计 |
| `platform-catalog/` | 商品、规格、分类、品牌 |
| `platform-inventory/` | 仓库、库存、采购、收退货、调拨、调整 |
| `platform-trade/` | 报价、订单、优惠、售后、支付退款 |
| `platform-finance/` | 采购付款、资金流水、对账 |
| `platform-integration/` | 存储、渠道、outbox投递、搜索适配 |
| `platform-app/` | 启动、控制器装配、安全链、定时任务、配置、Flyway |
| `web-storefront/` | 顾客商城，深色电竞主题 |
| `web-admin/` | 管理端工作台 |
| `docs/` | 本套文档、ADR、验收记录、变更记录 |
| `deploy/` | Compose、Nginx、环境模板、备份恢复说明 |

依赖原则：common无业务依赖；catalog/identity/inventory主要依赖common；trade可调用catalog和inventory公开服务；finance读取业务凭据可通过查询接口依赖trade/inventory；integration提供port实现，不让业务模块反向依赖其实现。app依赖并装配所有模块。禁止trade与finance互相编译依赖；收退款落账可在app级应用服务统一编排同一数据库事务，或把LedgerPort放common并由finance实现。

商品、库存、订单各自拥有自己的表写权限。跨模块通过公开服务接口，不直接注入其他模块Mapper。库存Service默认事务传播REQUIRED，加入订单创建事务；支付调用不能在该事务内执行。

### 3.1 接口与类的使用规则

| 类型 | 示例 | 为什么存在 |
|---|---|---|
| Controller类 | OrderController | 接收/校验请求、调用用例，避免业务SQL |
| 请求DTO类/record | OrderCreateRequest | 描述客户端能提交什么，不接受客户指定实付金额 |
| Service类 | OrderApplicationService | 事务、权限后的业务规则、流程编排 |
| 服务接口 | InventoryReservationService | 跨模块能力边界；不是每个类都必须一套接口+Impl |
| Mapper接口 | StockMapper | MyBatis代理生成实现；对应XML SQL |
| Entity/DO类 | StockDO | 对应数据库存储，不直接返回顾客 |
| 返回VO/record | OrderDetailResponse | 控制展示字段、脱敏及快照 |

教学Controller可采用用户熟悉的`@Autowired`字段注入，以便识别Service来源；主项目业务Service建议构造器注入，测试时依赖更明确。两者都由Spring注入对象，不是在每次请求里手工new业务服务。第一轮编码时选定主项目统一风格，后续AI不要反复改写无关模块。

## 4. 数据模型

### 4.1 通用字段与类型

- 主键BIGINT UNSIGNED自增并由后端转字符串；业务单号另设唯一索引，可用时间+随机/序列，不能只用当前毫秒。
- 大多数可变表有`created_at DATETIME(3)`、`updated_at DATETIME(3)`、`version BIGINT`；金额`BIGINT`按分存储；数量`INT`非负约束；状态`VARCHAR(32)`并通过应用枚举和约束校验。
- 业务单据保存`created_by`、状态时间和原因；事件/流水追加写，不做逻辑删除更新。
- 地址、商品规格、金额分摊快照可用JSON，不能仅引用会变的当前商品信息。
- 内部业务外键使用RESTRICT，禁止级联删除历史；外部交易号为字符串，不伪造外部主键。跨模块查询统一走公开QueryService。

### 4.3 库存表关键DDL示例

```sql
CREATE TABLE stock_balance (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  warehouse_id BIGINT UNSIGNED NOT NULL,
  sku_id BIGINT UNSIGNED NOT NULL,
  on_hand INT NOT NULL DEFAULT 0,
  reserved INT NOT NULL DEFAULT 0,
  quarantine INT NOT NULL DEFAULT 0,
  warning_threshold INT NOT NULL DEFAULT 5,
  version BIGINT NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL,
  updated_at DATETIME(3) NOT NULL,
  UNIQUE KEY uk_stock (warehouse_id, sku_id),
  CHECK (on_hand >= reserved AND reserved >= 0),
  CHECK (quarantine >= 0 AND warning_threshold >= 0)
);
```

该示例省略跨表FK，实际迁移按表创建顺序补齐。禁止依靠关闭约束解决脏数据。

## 5. 关键用例实现

### 5.1 下单事务

1. 认证顾客、读取属于本人的quote，检查过期和是否已创建订单。
2. 开启数据库事务；锁quote；读取当前SKU/券与快照比较。
3. 按确定顺序尝试仓库，按SKU ID升序锁stock_balance。只允许一个仓库满足全部行。
4. 预留库存使用带条件更新，并检查每行affectedRows=1。
5. 锁顾客券，AVAILABLE→HELD；插入订单/明细/地址和金额快照、reservation、流水、outbox；标记quote已用。
6. 与幂等成功结果同事务提交；返回订单。任一失败全部回滚。
7. 不在此事务中调用支付服务、搜索、消息队列或对象存储。

```sql
UPDATE stock_balance
SET reserved = reserved + :qty,
    version = version + 1,
    updated_at = UTC_TIMESTAMP(3)
WHERE warehouse_id = :warehouseId AND sku_id = :skuId
  AND on_hand - reserved >= :qty;
```

`:name`表示SQL解释占位符；实际MyBatis XML使用`#{name}`参数绑定，不用`${name}`拼接用户值。客户端排序只能映射到白名单列。

事务隔离初始建议READ COMMITTED，并发正确性通过显式锁、条件更新、唯一约束保证，不能把隔离级别当万能防护。发生死锁可对无外部副作用的完整事务有限重试（最多3次并抖动），不能重放真实支付动作。

### 5.2 金额算法

- 数量×单价使用Math.multiplyExact/addExact检查溢出；转换渠道十进制元金额时BigDecimal.movePointLeft(2)，禁止double。
- 固定券分摊按照需求文档最大余数法，最终各行折扣之和精确等于券额；使用BigInteger中间乘积或溢出受控的long范围。
- 部分退款以历史成交快照计算，不取当前售价；同一订单行的有效售后串行占用数量/金额。
- 退款申请回滚或撤销释放占用额度，已成功退款永不释放；重新申请重新计算剩余。最终退全时退款总额等于该行实付。

### 5.3 支付状态与事务边界

PaymentChannel接口建议：createPayment、queryPayment、closePayment、createRefund、queryRefund、verifyAndParseCallback。MOCK与真实沙箱各自实现。

外部请求前先持久化CREATED/PROCESSING与稳定商户单号；事务外调用；再开短事务写结果。网络超时结果未知，只能查单，不得立即重建新的支付单。

回调处理：验签和校验商户→根据paymentNo定位→锁订单→锁付款记录→校验金额/币种→插入去重事件→推进支付与订单→写finance_record和outbox→提交→ACK。同渠道交易号已成功处理时，即使eventId变化，也只能返回已处理结果；不能因订单后来已退款取消而重复创建迟到补偿退款。未处理成功不要返回渠道成功ACK。事件原文加密限期保存，不写普通日志。

关单先本地标CLOSING阻止新支付，再调用渠道关闭。最终取消与成功付款通过同一订单行锁串行化。已取消后可信成功不恢复订单：写异常收款、创建唯一补偿退款、告警。补偿退款无售后单，因此refund.after_sale_id可空。

退款额度包含已成功和处理中退款的总和；任何重试沿用同一个refundNo。失败状态不代表一定未退，先查询渠道再决定是否重发。

### 5.4 收货、发货和调拨

收货：锁采购单和明细→检查状态/累计量/送货单引用→入库与流水→更新累计已收→状态变化→outbox，全部同事务。

发货：锁订单→检查PAID/无有效售后→按SKU固定顺序锁库存/预留→扣实物和预留→标CONSUMED→插入唯一shipment→订单SHIPPED。重复请求读原shipment。

调拨审批预留源仓；发出时消费预留；目标收货时增加onHand。inTransit由SHIPPED未收的明细派生，可报表聚合，不在多个表中各维护一个不一致的总数。

统一锁顺序：先根业务单据，再按ID升序明细，再仓库ID/SKU ID升序库存，再优惠券/资金行。不同用例如果必须改变顺序，必须单独评审并加死锁重试测试。

### 5.5 幂等实现

- 拒绝请求前先完成认证和基本校验；业务操作建立幂等记录，唯一约束防并发。
- 请求摘要包含规范化路径/JSON和上传文件哈希；同键不同摘要409。
- 原请求处理中返回409+Retry-After，不能返回空成功；有超时恢复机制并核实业务唯一记录后恢复。
- 成功业务提交和幂等结果必须原子。对于外部渠道操作，幂等结果指向已持久化payment/refund记录，其状态可继续变化；重放返回原创建响应，客户端随后GET查询最新状态。
- 幂等记录默认24小时；订单quote唯一、送货单唯一、渠道交易唯一等业务约束长期保留，防止过期后重复过账。
- 不记录明文密码；登录/退出不采用业务幂等响应缓存；注册摘要需避免密码进入日志，使用服务端HMAC摘要。对包含个人地址的重放响应加密并限时清理。

## 6. 缓存、消息、搜索与任务

### 6.1 Redis

商品详情cache-aside，建议TTL 5–10分钟并随机抖动；提交商品变更后删除缓存，并通过outbox重复失效保证失败可重试。缓存版本号可减少旧值回填；下单始终读取数据库。热点key重建限并发，空结果短TTL避免穿透。

Redis用于认证时是硬依赖，故障认证返回503；商品缓存故障可读数据库但限流保护。不要把相同降级策略用于所有Redis用途。库存锁定不用Redis库存数作最终依据。

### 6.2 Outbox与RabbitMQ

核心事务内写outbox；投递器按next_retry_at捞取，使用锁/租约防重复抢占；收到broker确认后标记投递完成。崩溃窗口仍可能重复投递，消费者必须用consumed_event唯一记录保证幂等。

事件：ProductChanged、OrderPaid、OrderShipped、RefundSucceeded、StockChanged。payload含eventId、aggregateId、aggregateVersion、occurredAt、traceId。消费者与业务写操作同事务提交消费记录；不能先标已消费再执行。

指数退避、最大次数、死信队列、管理员重放与审计；建议初始最多10次，具体根据演练调整。不能把“发了一条消息”当成交付异步能力。

### 6.3 搜索

只索引可公开商品字段；商品更新事件带版本，旧事件不能覆盖新文档；下架事件使文档不可见。提供离线重建任务与原子别名切换脚本，首版不对普通用户暴露重建API。Elasticsearch故障时可降级数据库基础筛选并提示高级搜索暂不可用。

### 6.4 定时任务

订单超时扫描、支付/退款查单、outbox重试、优惠券到期、报价清理、导出文件过期清理。单实例也采用数据库任务租约，避免未来多实例重复执行。超时取消扫描不能直接删除支付中的订单。

CSV导出分批读取与流式写文件，设置最大时间范围和行数限制（建议10万行）；作业失败可重试，返回明确错误，不在HTTP请求内同步全量导出。

## 7. API和前端实现约束

以`05-openapi.yaml`生成TypeScript类型或客户端；后端DTO字段与合同保持一致。契约校验CI检查路径、必填项、枚举和响应信封漂移；不能以“代码能编译”代替接口一致性。

管理端和商城独立路由、主题及登录入口；共享金额格式化、HTTP客户端与类型库。前端金额字符串只作BigInt/精确十进制运算，最终计价仍依赖服务端。列表filters写入URL，详情返回保留上下文。

Vue 3 + TypeScript是本项目已选方案，理由是延续现有开发文档、减少技术分叉并把学习重点放在Spring Boot；不应宣称Vue组件库因原型静态而比React组件库性能更好。静态HTML原型不能用于判断框架性能。Vue/React的实际性能取决于组件结构、依赖体积、渲染方式、数据量和优化策略，需以构建体积与运行测量为依据。当前维持Vue 3；管理端用Element Plus并覆盖主题变量，商城用自建小型组件/设计令牌，避免把Element Plus风格直接带入商城。

工作台不要把所有业务数据塞进单个巨大DTO，也不要让每个卡片组件各自重复编写请求。通过统一API客户端、生成/维护的TypeScript接口类型和`useDashboardData()`组合层集中发起请求；待办计数调用`GET /admin/dashboard`，销售汇总及趋势调用`GET /admin/reports/sales`，近期订单与采购待办复用对应列表查询。对互相独立的数据请求并行执行并分别处理加载/空/错误状态（例如`Promise.allSettled`），某一块失败不应清空整个工作台。销售趋势必须使用接口返回的趋势点，不得把静态假曲线当作真实业务数据。只有在测量到请求数或首屏延迟确实成为瓶颈后，才新增工作台聚合API；聚合API只组合业务服务，不重复实现业务规则。

请求拦截器加入traceId（服务端可重新生成可信值）与Bearer；业务写操作在一次用户动作开始时生成幂等键，重试沿用。成功后新动作使用新键；不能每次HTTP重试生成新键。

401重新登录，409按业务错误展示并刷新，503查询已有单据，不弹“操作一定失败”。付款页使用退避轮询GET支付状态，页面跳转或URL参数不作为支付凭证。

安全：白名单CORS；HTTPS；参数化SQL；上传文件类型/大小/解码检查；下载鉴权；不信任客户端warehouseId；请求实体不绑定任意数据库字段。无认证Cookie不代表可以忽略XSS；不透明令牌仍需保护。

## 10. 本地启动与CI/CD设计

以下命令是未来仓库的目标工作流，当前没有仓库文件，因此尚不能直接运行。

```bash
# Maven Wrapper：编译并执行项目验证
./mvnw clean verify

# 启动基础依赖（deploy/compose.dev.yml需要在M0创建）
docker compose -f deploy/compose.dev.yml up -d mysql redis

# 打包后启动已配置的开发环境
java -jar platform-app/target/platform-app.jar --spring.profiles.active=dev
```

Windows对应`mvnw.cmd clean verify`。产物名在POM中固定为platform-app.jar，避免文档与实际文件名不同。前端各目录运行`npm ci`与`npm run dev`，使用已提交lockfile。

环境模板（只列键名，不放真实值）：DB_URL、DB_USERNAME、DB_PASSWORD、REDIS_HOST、REDIS_PASSWORD、APP_PUBLIC_BASE_URL、STORAGE_MODE、STORAGE_BUCKET、STORAGE_ACCESS_KEY、STORAGE_SECRET_KEY、PAYMENT_MODE、PAYMENT_APP_ID、PAYMENT_PRIVATE_KEY_FILE、PAYMENT_VERIFY_KEY_FILE、MQ_URI、SEARCH_URL。不同阶段仅启用必要配置；缺少生产关键凭据时启动失败并清楚报错。

dev/test默认MOCK；prod启动必须禁止mock-events路由、禁止弱默认账户与示例密码。SANDBOX只能连接沙箱域名，不能自动回退真实生产支付。

CI建议：依赖安装→静态编译→金额/状态单元测试→真实MySQL集成测试→OpenAPI漂移检查→前端构建→核心E2E→镜像构建。没有Docker执行条件的流水线需明确跳过集成测试并阻止标记发布验收完成。

部署：Nginx分别代理商城、管理端和`/api/`；Java后端仅内网暴露；MySQL/Redis/MQ/搜索不直接公网开放；Actuator公开仅最小健康状态，详细指标内网鉴权。JSON日志带traceId/businessNo，隐藏密码、令牌、支付密钥和完整地址。

数据库每日备份并演练恢复；RPO/RTO需部署资源明确后制定，不虚构承诺。Flyway采用向前兼容迁移，先加列后切换使用；已应用迁移不能修改。应用回滚不自动逆向删除数据库列，必要时写补偿迁移。

## 11. 监控与问题排查

监控：HTTP错误率/延时、连接池等待、死锁、数据库慢查询、outbox最老未投递时间、队列积压、退款PROCESSING时长、CLOSING订单时长、对账差异数、导出失败、磁盘与存储错误。

查询顺序：traceId→业务单号→状态日志→付款/退款→库存reservation/ledger→outbox/消费记录。排查不得直接手改库存或把订单强制改为PAID；修复动作必须保留原因、关联证据和审计记录。
