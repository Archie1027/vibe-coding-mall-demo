# 智采商城｜需求规格说明

版本：v0.2 · 日期：2026-10-20 · 状态：首版评审稿

用户确认项见产品文档U01–U10。以下精细业务规则是为使项目可实施而提出的默认设计，待对应模块开工时复核。本文件为状态、金额和库存规则的事实源。

## 1. 全局约定

- 单企业、人民币；数量为正整数；金额内部按人民币分的整数计算，Java用long；数据库BIGINT；API以十进制整数字符串传输，如`"129900"`代表1299元。禁止浮点金额。
- ID使用正整数字符串，避免浏览器大整数精度丢失。时间API使用带时区ISO 8601（如`2026-10-20T08:00:00Z`）；数据库保存UTC，界面按Asia/Shanghai显示。
- 数据库是订单、库存、付款的事实源。缓存、搜索索引和页面计数允许短暂延迟，但不能作为最终扣库存与计价依据。
- 业务单据不可直接删除；已记账记录不能修改金额，以关联冲正记录修正。基础资料仅停用，保留历史快照。
- 业务写接口使用`Idempotency-Key`（登录、退出与渠道回调除外）。作用域为主体+HTTP方法+规范化路径+键；同键同请求返回原结果，同键不同请求返回409。幂等键之外仍需业务唯一约束。
- 员工更新基础资料携带`version`，不一致返回409；读到旧状态后提交业务动作也返回409，不能覆盖新结果。

## 2. 权限与数据范围（FR-AUTH）

前端隐藏按钮仅用于体验，后端必须校验身份、权限码、资源归属、仓库范围和业务状态。

| 权限组 | 默认角色 | 规则 |
|---|---|---|
| `catalog:read/write` | 运营、管理员 | 维护商品/分类/品牌，不授予采购价访问 |
| `review:read` | 客服/运营/管理员按需授权 | 查询商品评价，遵循最小必要个人信息原则 |
| `review:moderate` | 客服/运营/管理员按需授权 | 审核评价；操作记录操作者、原因和结果 |
| `order:read` | 运营、客服、财务、仓管 | 仓管仅已分配仓库；客服字段脱敏 |
| `order:ship` | 仓管 | 必须拥有订单仓库权限 |
| `purchase:write/read` | 采购；主管/财务/仓管可授予read | 采购员仅本人；主管/财务全企业；仓管仅授权仓库的验收数据（含入库成本）；运营无采购价权限 |
| `purchase:approve` | 主管 | 全企业；不得审批本人提交单据 |
| `stock:read/receive/ship` | 仓管 | 仅授权仓库；收货与出货按动作独立授权 |
| `stock:adjust/approve` | 仓管/主管 | 调整制单人与审批人分离 |
| `transfer:write/approve` | 仓管/主管 | 出库时检查源仓权限，收货时检查目标仓权限 |
| `after-sale:read/review` | 客服 | 企业售后，最小必要个人信息 |
| `refund:execute`、`finance:read/write` | 财务 | 审核通过后才能退款；不能任意指定超额金额 |
| `promotion:write`、`report:read` | 运营/主管 | 财务成本指标单独限制财务权限 |
| `system:write`、`audit:read` | 管理员 | 角色/员工/设置；仍不能越过业务不变量 |

ADMIN默认拥有全部权限码，但采购自审禁止、状态限制、资金不可变规则仍生效。必须避免把仓库ID列表仅存前端。

登录默认：用户名3–32字符、密码12–72个UTF-8字节；密码哈希存储。邮箱非必填。访问令牌为服务端可撤销随机令牌，默认有效期2小时；仅通过Authorization Bearer发送。浏览器仅存内存，刷新需重新登录，这是首版体验取舍；后续持久登录单独设计。退出/停用员工/修改密码撤销相关令牌。登录限流与错误不泄露账户是否存在。

**验收 AUTH-01**：顾客A请求顾客B的订单、地址、支付或售后，返回404且不泄露资源存在性。**AUTH-02**：仓管修改请求中的warehouseId，不能读取或操作未授权仓库。**AUTH-03**：角色权限更新后服务端下一次请求按新权限校验。

## 3. 商品与媒体（FR-CAT）

- SPU为商品款型，SKU为可购买规格组合，如内存容量/颜色。SKU编码唯一，规格组合在同一SPU内唯一。
- 商品状态DRAFT/ON_SALE/OFF_SALE；上架需分类、名称、主图、至少一个启用且价格>0的SKU。无库存可展示但不能成交。
- SKU有售卖价和启用状态；采购成本仅在采购和财务数据中体现。历史订单保存名称、规格、单价、图片摘要，商品编辑不能改写历史订单。
- 分类最多3层，不允许循环；已有商品引用的分类仅停用。品牌仅停用。
- 图片上传限制JPEG/PNG/WebP、单张≤5MiB，验证实际文件类型与解码结果；服务器生成路径，不使用用户文件名作存储路径；商品详情不允许任意HTML脚本。
- 搜索支持关键词、分类、品牌、价格、排序；索引更新目标60秒以内。下单必须重新查数据库。

**CAT-01**：下架商品不再出现在公开列表，原订单仍能显示快照。**CAT-02**：篡改SKU售卖价不能改变最终下单金额。

## 3.1 商品评分与评价（FR-REVIEW，v1.0）

- v1.0包含基础商品评分/评价，不包含个性化推荐、评价点赞、复杂反作弊或AI自动审核。
- 顾客只能评价自己已完成（`COMPLETED`）订单中的订单明细；每个订单明细最多一条有效评价。后端必须校验订单归属与明细归属，不能信任前端传入的商品ID来证明购买关系。
- 评分为1–5整数星级；文字评价可选，最多2000字符；图片可选，最多5张，必须引用当前顾客有权使用的已上传媒体资源。输出时对文本进行转义，禁止任意HTML脚本。
- 新评价状态为`PENDING`，审核通过后变为`PUBLISHED`，审核驳回为`REJECTED`。只有`PUBLISHED`评价进入公开列表、商品平均分和评价数量；待审核/驳回评价不能影响公开评分。
- 顾客可查询自己的评价状态；被驳回的评价允许原作者修改后重新提交，其他用户不能查看其驳回原因或未公开内容。提交与重提均要求幂等键，重复提交不能生成多条评价。
- 后台评价审核需要`review:read`/`review:moderate`权限。驳回必须填写原因；审核动作记录到审计日志。前端隐藏审核按钮不代替后端授权校验。
- 商品列表可显示评分均值与评价数量；商品详情展示评分分布/评价列表及分页；订单完成后在订单详情提供评价入口。商城首页不强制展示评分/评价区，保持主视觉和商品发现流程简洁。
- 商品评分汇总在评价由`PENDING`变为`PUBLISHED`时，与评价状态在同一数据库事务中更新；v1.0暂不提供已公开评价撤下操作。未来若增加撤下公开评价的能力，必须在同一事务中反向更新评分汇总，避免统计长期漂移。

**REV-01**：未登录用户可查看已公开评价，但不能提交评价。**REV-02**：顾客不能评价他人订单或未完成订单。**REV-03**：同一订单明细并发提交两次最多创建一条评价。**REV-04**：待审核/驳回评价不计入商品平均分与评价数。**REV-05**：无`review:moderate`权限的员工审核请求返回403。**REV-06**：驳回缺少原因返回参数/业务校验错误；原作者可修改驳回内容并重新进入待审核状态。

## 4. 地址、购物车、报价与优惠（FR-CHECKOUT/FR-COUPON）

- 地址包含收件人、联系电话、省市区、详细地址；顾客最多20条，默认地址唯一。订单保存地址快照。
- 购物车同一用户同一SKU一条；数量1–99；提交结算前检查商品有效、数量和仓库供给。立即购买与购物车下单共享报价逻辑。
- `quote`返回不可变报价ID、金额明细、候选仓库、到期时间，默认5分钟有效；报价不锁库存。提交时重算和复核版本；价格、券条件或仓库发生变化返回`QUOTE_CHANGED`并提示重新确认，不偷偷改价。
- 满减券：模板包含门槛、面额、有效期、发放总量、每人最多1张；面额>0且≤门槛，门槛允许等于面额。领取采用原子计数及唯一约束。
- 券状态AVAILABLE/HELD/USED/EXPIRED。创建订单占用；支付成功核销；未支付取消时按当前时间释放为AVAILABLE或EXPIRED。已支付退款不退券，页面明确提示。
- 按商品行原金额分摊优惠：先向下取整，再按余数从大到小补分，余数相同按SKU ID排序；每行金额和折扣快照持久化，保证分摊和等于券面额。
- 包邮、无其他叠加优惠；应付=商品总额−优惠。为简化渠道处理，首版应付必须>0；若优惠使金额为0则拒绝选券并提示。

**CHK-01**：两次并发使用同一张券，最多一个订单占用。**CHK-02**：报价后调价，创建订单返回409，不产生订单、不锁库存。**CHK-03**：前端计算出的金额仅展示，服务器按商品和报价计算。

## 5. 多仓库存与单仓履约（FR-STOCK）

### 5.1 库存量定义

| 字段 | 定义 |
|---|---|
| onHand | 仓库内可售实物量，不包含隔离品 |
| reserved | onHand中已为订单或调拨预留的量 |
| available | 派生值onHand−reserved，不独立维护 |
| quarantine | 仓内隔离量，例如售后待检或损坏品，不可销售 |
| inTransit | 已出源仓未入目标仓的调拨量，按调拨明细统计 |

恒有onHand≥reserved≥0、quarantine≥0。同一warehouseId+skuId唯一。库存流水记录变更前后、四类变化量、业务类型/单据/明细、操作者、时间；无需记负数的“可用库存”。

### 5.2 订单选仓

按启用且允许电商履约的仓库priority升序、ID升序逐个评估，找到能满足所有订单行的一个仓库。创建订单事务中按仓库+SKU固定顺序锁行并复核。不能满足则换候选仓库重新尝试有限次；仍失败返回`NO_SINGLE_WAREHOUSE`或`STOCK_INSUFFICIENT`。

跨仓合计足够但单仓不足时不能创建订单；页面提示无单仓可完整发货，用户可调整商品或稍后再试。后台可先调拨，不能让前端偷偷拆成多笔订单。订单创建后warehouseId固定，首版不支持改仓。

### 5.3 库存动作

- 创建订单：reserved增加。
- 支付成功：库存数量不变，预留继续保留到发货。
- 确认未支付取消：reserved减少。
- 发货：onHand和reserved同时减少，生成一条出库流水。
- 全单发货前退款完成：释放reserved；付款结果未知或退款处理中不释放。
- 采购收货：onHand增加；不合格到货不计入可接受数量。
- 售后退回收货：quarantine增加；库存调整审批后可转为onHand或损耗减少。
- 调拨批准：源仓reserved增加；发出：源仓onHand/reserved减少、在途增加；收货：目标仓onHand增加、在途减少。

**STK-01**：库存1，100个不同订单请求竞争，最多1笔成功预留。**STK-02**：重复发货不二次扣库存。**STK-03**：多行订单后一个SKU不足，前面SKU的预留也回滚。**STK-04**：跨仓合计足够但无单仓满足，明确拒单。

## 6. 订单状态（FR-ORDER）

| 当前状态 | 动作/条件 | 下一状态 | 库存/金额影响 |
|---|---|---|---|
| UNPAID | 可信支付成功 | PAID | 券HELD→USED，写入收款记录 |
| UNPAID | 取消或超时；存在未终态渠道支付 | CLOSING | 暂不释放，先关单/查单 |
| UNPAID | 取消或超时；无任何活跃渠道支付 | CANCELLED | 原子释放库存及券 |
| CLOSING | 查单证实付款成功 | PAID | 按成功流程处理 |
| CLOSING | 所有支付尝试确认关闭或失败 | CANCELLED | 释放库存及券 |
| PAID | 一次完整发货；无有效阻塞售后 | SHIPPED | 扣除预留及实物库存 |
| SHIPPED | 顾客确认收到 | COMPLETED | 写完成时间 |
| PAID | 发货前全单退款成功 | CANCELLED | 释放预留；已用券不返还 |

发货后退款不改变订单履约状态，订单另外显示退款金额和售后状态。首版不自动确认收货，不支持部分发货。金额变更须经退款单，不直接编辑订单总额。

超时扫描以数据库expiresAt为准；任务延迟不应允许过期订单创建新支付。CLOSING可能持续等待外部结果，后台展示“支付核实中”，不能伪装成已取消。

## 7. 支付、关单、退款（FR-PAY）

### 7.1 支付尝试

支付记录与订单独立，一笔订单允许多个历史尝试，但同一时刻最多一个活跃尝试。状态CREATED/PROCESSING/SUCCEEDED/FAILED/CLOSED。启动支付前校验归属、订单状态、到期时间和应付金额。

模拟渠道MOCK仅dev/test开放，模拟成功、失败和重复事件。SANDBOX是待选真实服务商的适配接口，不是假设存在统一第三方请求格式。调用服务商超时进入PROCESSING并查询，不能立刻当失败。

回调必须：使用原始报文验签→校验应用/商户、商户单号、渠道交易号、币种和金额→锁支付与订单→持久化唯一渠道事件→推进状态→写资金流水与outbox。前端“支付成功”跳转不能直接确认订单。

### 7.2 关闭与迟到回调

先在本地把订单推进CLOSING并阻止新支付，再在事务外调用渠道关闭；结果成功/已关闭时本地释放，结果已支付时确认付款，未知时持续查单。所有历史尝试均需终态后才能取消。

渠道异常导致已CANCELLED订单收到可信成功时：记录异常收款并建立补偿退款任务，订单保持CANCELLED，不自动重新预留/发货；告警并对账。重复回调不重复建退款任务。此补偿退款不需要顾客售后单，但必须有关联付款与异常原因。

### 7.3 退款

退款状态CREATED/PROCESSING/SUCCEEDED/FAILED。业务退款金额由已审核售后计算，客户端不能指定任意金额；补偿退款由系统计算。退款“申请受理”不等于成功。只有查询/回调确认SUCCEEDED才记退款资金流水与推进售后。

同一付款成功退款总额+处理中预占退款额≤实付。重试先查渠道结果；使用同一商户退款号保证渠道幂等，不能每次失败都换号。永久失败转人工核实，库存和订单不能假装退款完成。

**PAY-01**：同回调20次只记一次收款。**PAY-02**：回调金额与订单不符不置PAID。**PAY-03**：超时关单与成功回调竞争最终只有一种可解释结果。**PAY-04**：已取消订单迟到付款生成一次补偿退款，不恢复订单。**PAY-05**：退款接口超时后重试不重复退钱。

## 8. 发货与售后（FR-AFTERSALE）

- 发货必须PAID、仓库授权、整单可发、无REQUESTED/APPROVED/REFUNDING等有效发货前售后；记录物流公司、运单号、发货人。默认人工物流，无实时轨迹。
- 顾客可在PAID时申请`CANCEL_BEFORE_SHIP`，范围必须整单、未发货。SHIPPED/COMPLETED可申请`RETURN_REFUND`，一张售后单针对一个订单明细的若干件。已完成订单仅7天窗口内可申请，发货未完成不应用收货后截止时间。
- 客服可驳回，必须原因。售后未处理时顾客可撤销；已开始退款不可撤销。发货前售后进入活跃状态后阻止发货，驳回/撤销后解除。
- 已发货部分退货最大可申请数量=购买数量−已成功退货退款数量−其他活跃售后占用数量，采用锁控制。
- 部分退款以该订单行分摊后的实付为基准，按累计退款量计算差额：本次= floor(行实付×累计批准数量/购买数量)−历史已分配金额。全部退回时总额精确等于行实付；事务内占用数量与金额，失败重试沿用原金额。
- 退货物流先由顾客提交；仓管验收必须数量与申请一致，差异需客服先纠正/重审，不能擅自超额收货。退回实物全部进入quarantine。后续通过审批的`RELEASE_QUARANTINE`调整转可售；损坏通过`SCRAP_QUARANTINE`减少隔离量。
- 发货前退款没有实物回库；退款成功后只释放reserved。发货后退款不自动增加可售库存，入库由退货验收独立驱动。

| 状态 | 后续合法状态 |
|---|---|
| REQUESTED | APPROVED（取消发货）、WAIT_RETURN（退货）、REJECTED、CANCELLED |
| WAIT_RETURN | RECEIVED（已提交退货运单且仓管实收）；提交运单自身不改状态 |
| APPROVED / RECEIVED | REFUNDING |
| REFUNDING | COMPLETED；退款失败保持REFUNDING并展示退款FAILED |
| COMPLETED / REJECTED / CANCELLED | 终态 |

**AS-01**：售后申请与发货并发，串行化后不得既退款取消又发货。**AS-02**：分次退货累计不超过购买数量与实付。**AS-03**：重复验收不重复增加隔离库存。

## 9. 采购、入库与采购退货（FR-PURCHASE）

采购单含供应商、目标仓库、币种CNY、SKU、数量、正数采购单价；提交后不可直接改数量和单价，驳回后可修改并重新提交。状态DRAFT→SUBMITTED→APPROVED→PART_RECEIVED→RECEIVED；SUBMITTED可到REJECTED；REJECTED经编辑回DRAFT；APPROVED/PART_RECEIVED可由主管关闭余量为CLOSED，原因必填。

审批不能自审。入库单一次提交即完成过账：采购单状态必须APPROVED/PART_RECEIVED；本批数量>0；累计接受量≤批准量；目标仓库必须一致；多行部分错误整单回滚。单据包含deliveryReference（供货送货单号），同供应商+采购单+送货单号唯一，防止换幂等键重复入库。满量后自动RECEIVED。

采购退货针对已过账入库明细，数量不超过其已收−已退；且仓库available足够。首版提交即过账，操作权限为仓管，需填写原因与供应商退货凭据。扣onHand、生成采购退货单、减少应结算金额；不重新打开原采购单，也不减少原始“累计收货量”。

已收量与净保留量分别展示。采购关闭不撤销已收与已付款记录。超额付款因退货产生时列为供应商待退金额，可录入供应商退款记录处理。

**PUR-01**：采购100，收60、收40后完成；再收1拒绝。**PUR-02**：采购本人审批拒绝。**PUR-03**：退货不使已完成采购单重新可收货。**PUR-04**：采购关闭后不能继续收货。

## 10. 调拨与库存调整（FR-TRANSFER/FR-ADJUST）

调拨：DRAFT→SUBMITTED→APPROVED→SHIPPED→RECEIVED；SUBMITTED可REJECTED，REJECTED编辑后回DRAFT；DRAFT/SUBMITTED/APPROVED可CANCELLED。批准时预留源仓库存，批准后取消释放；已SHIPPED禁止取消。首版整批发出和整批接收，不支持短收/分批；差异挂异常并人工核实，不允许输入假收货量抹平。

制单需要源仓权限；发货需源仓权限；收货需目标仓权限。源仓≠目标仓，批准时两仓启用。审批人不得为提交人。每个动作都写审计和库存流水。

库存调整：创建PENDING，主管批准→POSTED，驳回→REJECTED。原因、证据附件（可选）和明细必填，操作者不能自审。

类型：COUNT_GAIN增加onHand；COUNT_LOSS减少onHand且不能低于reserved；RELEASE_QUARANTINE隔离转可售；SCRAP_QUARANTINE扣隔离。每行quantity>0，审批时重查数量，失败整单不批准。

**TR-01**：源仓发出10后源仓减少10、在途10，目标收后增加10且在途0。**ADJ-01**：试图盘亏已被订单预留部分失败，不破坏预留。

## 11. 资金记录与业务对账（FR-FINANCE）

资金分类：ORDER_RECEIPT、ORDER_REFUND、PURCHASE_PAYMENT、SUPPLIER_REFUND、REVERSAL。记录方向IN/OUT、正金额、币种、关联业务单据、渠道/凭据、发生时间、操作者。收款/退款自动按可信渠道终态生成；采购付款和供应商退款由财务录入线下凭据，不调用真实银行转账。

采购付款上限=已接受收货金额−采购退货金额−净已付，首版不支持预付款；退货后已付超过净应付形成供应商待退。供应商退款≤待退。错误人工记录以反向流水冲正，原记录保留，同一记录最多冲正一次；自动渠道流水不能人工冲正替代渠道退款。

对账首版支持上传标准化CSV（date,type,channelTransactionId,businessNo,amountMinor,currency）；MOCK可生成等价测试文件。财务选择日期/渠道创建任务，区间按上海自然日解释；对比本地渠道终态流水和导入账单，按交易ID匹配金额、币种、类型。

差异包括仅本地存在、仅渠道存在、金额不符、币种不符、重复行。对账状态PENDING/RUNNING/SUCCEEDED/FAILED；任务成功表示完成比对，不表示零差异。差异OPEN/RESOLVED；关闭必须填写原因和处理证据，不直接改原交易。重复上传同日期+渠道+文件哈希复用已有任务。CSV公式开头内容导出时转义，避免表格公式执行。

**FIN-01**：退款受理中不记成功退款流水。**FIN-02**：差异关闭后仍保留原差异、处理人和说明。**FIN-03**：采购退货导致超付时展示待退，不自动假造供应商退款。

## 12. 通知、报表、设置（FR-OPS）

- 站内通知：订单付款/发货、售后结果、低库存；事件ID+收件人+通知类型唯一。邮件/短信不属于首版承诺。
- 报表：支付成功总额、成功退款总额、净实收=两者差；采购付款独立列示；不把净实收命名为利润。库存预警按available与SKU/仓库阈值比较。
- 销售报表按支付成功时间统计收款、按退款成功时间统计退款，可能出现当日净实收为负。时间筛选为左闭右开。
- 导出：后台创建任务，状态PENDING/RUNNING/SUCCEEDED/FAILED；返回过期下载链接。仅导出当前主体可见范围；个人信息最小化；日志记录申请人和条件。首版交付CSV，不承诺Excel模板导入。
- 系统设置仅白名单字段：订单支付有效分钟、售后窗口天数、报价有效秒、默认库存预警阈值。已创建订单保存expiresAt，设置变更不追改历史。

## 14. 端到端验收剧本

1. 创建两仓A/B、采购员、主管、仓管、财务、顾客；校验角色与仓库范围。
2. 采购A仓键盘100件，审批后分60+40两次入库，库存可用100；重复收货请求不增加库存。
3. 调拨A→B 20件，批准后A可用80、预留20；发出后A实物80/预留0、在途20；收货后B实物20。
4. 顾客购买A仓可完整满足的商品组合，创建订单后预留，成功付款不减实物；发货后才扣实物。
5. 另一订单超时，查渠道确认关闭后释放。模拟迟到成功，进入一次补偿退款而不是重新发货。
6. 收货后对订单一行申请部分退货；退货验收进入隔离，退款成功生成资金流水；批准转可售后增加onHand。
7. 财务按采购已收金额录入付款；供应商退货导致超付时录入退款；导入含一条差异的账单并处理差异。
8. 从业务单据跳转库存流水、付款退款、操作日志；三处数额一致。

演示种子数据、模拟结果及报表必须明确标记为演示，不混入真实收付款环境。
